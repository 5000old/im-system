# IM 即时通讯系统软件详细设计说明书

## 1 详细设计概述

### 1.1 设计目标

本说明书基于已评审通过的《IM 即时通讯系统概要设计说明书》开展细化设计，在不改动整体架构、不新增业务需求的前提下，将宏观模块拆解为可直接落地编码的粒度，明确各模块内部执行逻辑、接口规范、数据结构、数据库表结构及核心业务时序，保障代码开发可遵循、功能测试可对标、项目验收可量化。 本设计严格遵循高内聚、低耦合原则，全程基于 C++ 技术栈实现，聚焦即时通讯核心业务特性，满足 100 人并发在线、消息投递时延≤400ms 的性能指标，适配本科软件工程毕业设计评审标准。

### 1.2 设计范围

本设计覆盖系统全部核心业务模块，包括用户登录与状态管理、点对点私聊、群聊管理、系统管理员管控、网络通信、数据持久化、客户端 UI 交互共 7 个模块；涵盖模块内部逻辑、内外接口、内存数据结构、数据库存储、核心业务时序、性能资源控制、单元测试要点共 7 个设计维度。 本设计不超出概要设计边界：不实现用户注册、多媒体消息、数据加密、高可用集群等扩展功能；不引入 Redis、消息队列等额外中间件；仅聚焦文本型即时通讯核心业务闭环。

### 1.3 前置依赖

1. 已确认的《软件需求规格说明书（SRS）》功能与非功能需求
2. 已评审通过的概要设计结论：C/S 分层架构、单服务端多客户端部署、三类角色权限体系、数据库 + 内存双层存储方案
3. 技术栈约束：C++11 及以上版本、TCP 长连接、轻量关系型数据库、桌面端轻量化 UI 框架
4. 性能指标基线：100 用户并发、消息投递时延≤400ms、状态同步时延≤500ms

### 1.4 IM 系统设计侧重点

1. **消息可靠性**：通过全局唯一消息 ID、服务端持久化、离线消息存储、重连补发机制保障消息不丢失
2. **消息有序性**：通过报文序列号、服务端时间戳、单连接串行发送保障消息按发送顺序投递
3. **弱网容错性**：通过本地缓存、指数退避重连、超时重试、报文去重适配网络波动场景
4. **并发支撑性**：通过 IO 多路复用、多线程任务分离、连接池、内存缓存支撑 100 用户并发
5. **权限隔离性**：服务端统一前置权限校验，严格隔离普通用户、群主、系统管理员三类角色权限边界
6. **可维护性**：模块职责单一，接口标准化，分层调用单向闭环，便于测试与迭代

## 2 各功能模块详细设计

### 2.1 用户登录与状态管理模块

#### 2.1.1 模块功能详述

本模块负责用户身份校验、在线状态生命周期管理、用户信息同步及封禁拦截，是系统接入的入口模块。核心能力包括：预设账号合法性校验、封禁账号登录拦截、在线 / 离线状态切换与全网广播、用户昵称修改与同步、心跳保活与超时判定、强制踢下线处理。 模块横跨客户端业务层、服务端业务层与权限管控层，客户端负责发起请求与本地状态渲染，服务端负责权威校验与状态同步。

#### 2.1.2 模块输入输出

表格

| 方向 | 输入项                             | 数据来源              | 说明                     |
| ---- | ---------------------------------- | --------------------- | ------------------------ |
| 输入 | 登录请求（用户 ID、客户端版本）    | 客户端 UI 层          | 用户输入预设账号发起登录 |
| 输入 | 心跳保活报文                       | 客户端通信层          | 定时发送维持在线状态     |
| 输入 | 昵称修改请求（新昵称）             | 客户端 UI 层          | 用户主动修改昵称         |
| 输入 | 用户登出请求                       | 客户端 UI 层          | 用户主动退出登录         |
| 输入 | 用户封禁指令                       | 权限管控层            | 管理员发起封禁后触发     |
| 输出 | 登录响应（结果码、用户信息、角色） | 服务端→客户端         | 返回登录成功 / 失败原因  |
| 输出 | 用户状态同步通知                   | 服务端→全量在线客户端 | 广播用户上下线状态       |
| 输出 | 昵称更新通知                       | 服务端→全量在线客户端 | 广播用户最新昵称         |
| 输出 | 强制踢下线通知                     | 服务端→对应用户客户端 | 封禁时强制终端退出       |
| 输出 | 心跳响应                           | 服务端→客户端         | 回应心跳保活请求         |

#### 2.1.3 内部执行逻辑

1. 登录校验流程
   1. 客户端捕获用户输入的账号 ID，封装登录报文通过通信层发送至服务端
   2. 服务端通信层解析报文，分发至用户状态管理模块
   3. 模块调用数据持久层接口查询用户基础信息，校验账号是否存在
   4. 调用权限管控层接口校验账号封禁状态，若已封禁直接返回封禁错误码
   5. 校验通过后，在服务端内存在线用户表中新增用户记录，绑定连接 ID，更新最后心跳时间
   6. 向所有在线客户端广播该用户上线通知
   7. 向当前客户端返回登录成功响应，携带用户昵称、角色信息
   8. 异步查询该用户离线消息，触发离线消息补发流程
2. 心跳与状态判定流程
   1. 客户端每 15 秒向服务端发送一次心跳报文
   2. 服务端收到心跳后，更新对应用户的最后心跳时间戳，返回心跳响应
   3. 服务端启动独立心跳检测线程，每 5 秒遍历在线用户表，若用户最后心跳时间距当前超过 30 秒，判定为离线
   4. 判定离线后，从内存在线用户表移除记录，解绑连接，向所有在线客户端广播该用户离线通知
   5. 客户端若连续 3 次未收到心跳响应，判定连接断开，触发重连流程
3. 昵称修改流程
   1. 客户端发起昵称修改请求，携带新昵称
   2. 服务端校验昵称长度（1-32 字符）与合法性，校验用户登录状态
   3. 校验通过后更新数据库用户表昵称字段与更新时间
   4. 更新内存在线用户表中的昵称缓存
   5. 向所有在线客户端广播该用户昵称更新通知
   6. 向请求客户端返回修改成功响应
4. 封禁踢线流程
   1. 权限管控层下发用户封禁指令
   2. 用户状态模块查询该用户是否在线，若在线则通过通信层发送踢下线通知
   3. 关闭对应用户连接，从在线用户表移除，更新数据库封禁状态
   4. 向全网广播该用户离线通知

#### 2.1.4 核心业务规则

1. 仅预设账号可登录，无自主注册功能，账号 ID 全局唯一
2. 用户在线状态仅分为在线、离线两种，无忙碌、隐身等扩展状态
3. 心跳超时阈值 30 秒，连续 3 次心跳丢失判定连接断开
4. 昵称修改实时全网同步，所有客户端界面统一刷新
5. 封禁账号登录直接拦截，在线封禁用户强制踢下线且无法再次登录

#### 2.1.5 依赖的外部资源

- 外部模块：网络通信模块、数据持久化模块、权限管控模块
- 数据库资源：用户信息表
- 内存资源：在线用户哈希表、连接会话映射表

#### 2.1.6 异常场景处理

1. **登录超时**：客户端 5 秒未收到登录响应，提示登录超时，允许用户重新发起
2. **重复登录**：同一账号二次登录时，服务端踢掉前一连接，返回 “账号已在别处登录”
3. **心跳丢失**：单次心跳丢失不做处理，连续 3 次丢失触发连接断开与重连
4. **昵称修改失败**：服务端返回错误码（长度超限、含敏感词），客户端本地回滚昵称显示
5. **状态同步失败**：客户端未收到状态通知时，以服务端数据为准，重连后重新拉取用户列表

### 2.2 点对点私聊模块

#### 2.2.1 模块功能详述

本模块实现一对一文本消息全生命周期管理，是即时通讯核心业务模块。核心能力包括：实时消息收发、离线消息缓存与上线自动投递、历史消息加载、2 分钟内消息撤回、本人消息删除、整会话删除、新消息通知提示、发送失败状态展示。 所有业务规则由服务端统一判定，客户端仅做展示与本地缓存，避免客户端篡改逻辑。

#### 2.2.2 模块输入输出

表格

| 方向 | 输入项                                    | 数据来源        | 说明                 |
| ---- | ----------------------------------------- | --------------- | -------------------- |
| 输入 | 私聊消息发送请求（接收者 ID、消息内容）   | 客户端 UI 层    | 用户输入消息并发送   |
| 输入 | 历史消息拉取请求（对方用户 ID、拉取数量） | 客户端 UI 层    | 进入会话时加载历史   |
| 输入 | 消息撤回请求（消息 ID）                   | 客户端 UI 层    | 用户撤回已发送消息   |
| 输入 | 消息删除请求（消息 ID）                   | 客户端 UI 层    | 用户删除本人单条消息 |
| 输入 | 会话删除请求（对方用户 ID）               | 客户端 UI 层    | 用户删除整条私聊会话 |
| 输出 | 消息发送响应（结果码、消息 ID、发送时间） | 服务端→发送方   | 返回发送结果         |
| 输出 | 私聊消息推送                              | 服务端→接收方   | 实时推送新消息       |
| 输出 | 历史消息列表                              | 服务端→客户端   | 返回指定数量历史消息 |
| 输出 | 消息撤回通知                              | 服务端→收发双方 | 通知消息已撤回       |
| 输出 | 会话删除确认                              | 服务端→请求方   | 返回会话删除结果     |

#### 2.2.3 内部执行逻辑

1. 消息发送与投递流程
   1. 客户端用户输入消息，点击发送，客户端业务层生成临时消息 ID，本地先展示为 “发送中”
   2. 封装私聊消息发送报文，通过通信层发送至服务端
   3. 服务端通信层解析报文，分发至私聊业务模块
   4. 校验发送者登录状态、接收者账号是否存在，校验消息内容长度（1-1024 字符）
   5. 生成全局唯一 64 位消息 ID，记录发送时间戳，写入消息记录表（状态为正常）
   6. 查询接收者在线状态：
      - 在线：直接通过通信层向接收者推送私聊消息报文
      - 离线：写入离线消息表，待用户上线后补发
   7. 向发送方返回消息发送成功响应，携带正式消息 ID 与服务端时间
   8. 客户端收到成功响应后，更新本地消息状态为 “已发送”；若收到失败响应，显示红色感叹号
2. 历史消息加载流程
   1. 用户进入私聊会话，客户端向服务端发起历史消息拉取请求，默认拉取最近 20 条
   2. 服务端校验用户权限，查询消息记录表中该会话的消息，按发送时间倒序返回
   3. 客户端收到后按时间正序渲染到界面，过滤已删除、已撤回消息的展示
3. 消息撤回流程
   1. 用户发起撤回请求，携带目标消息 ID
   2. 服务端查询消息记录，校验发送者是否为当前用户、消息是否已撤回 / 删除
   3. 服务端计算消息发送时间与当前时间差，超过 2 分钟则返回 “撤回超时” 错误
   4. 校验通过后，更新消息状态为 “已撤回”
   5. 向收发双方客户端推送消息撤回通知
   6. 双方客户端界面将对应消息替换为 “对方已撤回”/“你已撤回” 提示
4. 会话删除流程
   1. 用户发起删除整条私聊会话请求
   2. 服务端校验用户身份，开启数据库事务
   3. 删除该会话对应的所有消息记录、会话信息记录
   4. 事务提交后返回删除成功响应
   5. 客户端本地清空该会话所有缓存数据，从会话列表移除

#### 2.2.4 核心业务规则

1. 消息 ID 全局唯一，由服务端生成，用于去重、撤回、删除定位
2. 撤回时效严格由服务端校验，阈值为 120 秒，客户端计时仅作参考
3. 用户删除本人消息为软删除：仅标记消息状态，客户端不展示，管理员仍可查询
4. 删除整条会话为硬删除：彻底清除数据库中对应会话所有数据，不可恢复
5. 离线消息按发送时间顺序投递，不打乱消息时序
6. 消息发送失败仅在发送方展示失败标识，不影响接收方

#### 2.2.5 依赖的外部资源

- 外部模块：网络通信模块、用户状态管理模块、数据持久化模块
- 数据库资源：消息记录表、会话信息表、离线消息表
- 内存资源：在线用户缓存

#### 2.2.6 异常场景处理

1. **消息发送超时**：客户端 3 秒未收到发送响应，自动重试 1 次，仍失败则标记为发送失败
2. **弱网断连**：消息发送时网络断开，客户端本地缓存未发送消息，重连成功后自动补发
3. **消息重复接收**：客户端通过消息 ID 去重，重复推送的消息直接丢弃，不重复渲染
4. **历史消息拉取失败**：提示加载失败，用户可手动下拉刷新重试
5. **撤回消息已不存在**：服务端返回消息不存在错误，客户端提示撤回失败

### 2.3 群聊管理模块

#### 2.3.1 模块功能详述

本模块实现多人群聊全业务流程，支撑群组生命周期管理与群内消息交互。核心能力包括：普通用户创建群组、群主移除成员、全员邀请成员、主动退群、全员修改群名称、群消息收发、群历史消息加载、群消息撤回 / 删除、群解散通知接收。 群主仅拥有单群局部管理权限，群解散权限仅归系统管理员所有。

#### 2.3.2 模块输入输出

表格

| 方向 | 输入项                               | 数据来源              | 说明               |
| ---- | ------------------------------------ | --------------------- | ------------------ |
| 输入 | 建群请求（群名称、初始成员列表）     | 客户端 UI 层          | 用户发起创建群组   |
| 输入 | 邀请成员请求（群 ID、被邀请用户 ID） | 客户端 UI 层          | 群成员邀请新用户   |
| 输入 | 移除成员请求（群 ID、被移除用户 ID） | 客户端 UI 层          | 群主踢除群成员     |
| 输入 | 退群请求（群 ID）                    | 客户端 UI 层          | 用户主动退出群组   |
| 输入 | 群名称修改请求（群 ID、新群名）      | 客户端 UI 层          | 群成员修改群名称   |
| 输入 | 群消息发送请求（群 ID、消息内容）    | 客户端 UI 层          | 用户发送群消息     |
| 输入 | 群解散指令                           | 系统管理员管控模块    | 管理员强制解散群   |
| 输出 | 建群响应（群 ID、群信息）            | 服务端→创建者         | 返回建群结果       |
| 输出 | 群成员更新通知                       | 服务端→所有群成员     | 通知成员增减       |
| 输出 | 群名称更新通知                       | 服务端→所有群成员     | 通知群名变更       |
| 输出 | 群消息推送                           | 服务端→所有在线群成员 | 实时推送群内新消息 |
| 输出 | 群解散通知                           | 服务端→所有群成员     | 通知群组已解散     |

#### 2.3.3 内部执行逻辑

1. 创建群组流程

   1. 用户填写群名称、选择初始成员，发起建群请求
   2. 服务端校验创建者登录状态，校验初始成员账号合法性
   3. 校验通过后，在群组信息表插入记录，生成群 ID，设置创建者为群主
   4. 批量插入群成员记录（创建者 + 所有初始成员）
   5. 向所有群成员推送建群成功通知与群信息
   6. 向创建者返回建群成功响应，携带群 ID

2. 群成员管理流程

   - 邀请成员

     ：

     1. 群内任意用户发起邀请，携带群 ID 与被邀请用户 ID
     2. 服务端校验群状态是否正常、邀请者是否在群内
     3. 校验被邀请用户是否已在群内，若已在则返回 “已在群中”
     4. 校验通过后新增群成员记录，向所有群成员推送成员更新通知
     5. 向被邀请用户推送入群通知

   - 移除成员

     ：

     1. 群主发起移除请求
     2. 服务端校验请求者是否为群主、被移除用户是否在群内
     3. 校验通过后删除群成员记录，向所有群成员推送成员更新通知
     4. 向被移除用户推送 “你已被移出群聊” 通知

   - 主动退群

     ：

     1. 用户发起退群请求
     2. 服务端校验用户是否在群内，校验群主不可直接退群
     3. 删除该用户群成员记录，若退群者为群主，则自动指定群内入群时间最早的成员为新群主
     4. 向所有群成员推送成员更新通知

3. 群消息收发流程

   1. 用户在群内发送消息，客户端封装群消息发送请求
   2. 服务端校验发送者是否在群内、群状态是否正常
   3. 校验通过后生成全局消息 ID，写入消息记录表（消息类型为群聊）
   4. 批量查询群内所有成员的在线状态
   5. 向在线成员实时推送群消息，向离线成员写入离线消息表
   6. 向发送方返回消息发送成功响应

4. 群解散处理流程

   1. 接收系统管理员下发的群解散指令
   2. 更新群组状态为 “已解散”，不物理删除群组数据
   3. 向所有在线群成员推送群解散通知
   4. 离线成员上线后，拉取群列表时同步更新群状态
   5. 群解散后禁止发送新消息，历史消息保留供管理员查询

#### 2.3.4 核心业务规则

1. 建群者自动成为群主，群主身份唯一，仅拥有本群成员移除权限
2. 所有群成员均可邀请新成员、修改群名称，操作实时全网同步
3. 群解散为软状态变更，历史数据永久留存，仅禁止新消息发送
4. 群消息撤回规则与私聊一致：发送者 2 分钟内可撤回
5. 群成员上限默认 100 人，适配系统并发规模
6. 群消息批量推送时，单个成员推送失败不影响其他成员

#### 2.3.5 依赖的外部资源

- 外部模块：网络通信模块、用户状态管理模块、数据持久化模块、系统管理员管控模块
- 数据库资源：群组信息表、群成员表、消息记录表、离线消息表
- 内存资源：在线用户缓存、活跃群组缓存

#### 2.3.6 异常场景处理

1. **群操作无权限**：返回明确错误码（非群主踢人、已解散群发言），客户端提示对应原因
2. **群消息批量推送异常**：采用异步队列逐个推送，单个连接失败跳过，不阻塞整体流程
3. **邀请已在群成员**：返回重复入群错误，不重复添加成员记录
4. **群解散通知丢失**：客户端重连后拉取群列表，服务端返回最新群状态，本地同步更新
5. **大群消息风暴**：单群每秒消息超过 20 条时，服务端限流，返回发送频繁提示

### 2.5 网络通信模块

#### 2.5.1 模块功能详述

本模块是系统的通信底座，采用抽象层 + 底层实现的隔离设计，屏蔽底层网络细节，为上层业务提供统一的收发接口。核心能力包括：TCP 长连接管理、IO 多路复用并发处理、报文封装与解析、粘包拆包处理、心跳检测、断连重连、消息去重、消息转发调度。 模块分为客户端通信层与服务端通信层，两层协议完全一致，底层实现可无缝替换。

#### 2.5.2 模块输入输出

表格

| 方向 | 输入项                                          | 数据来源     | 说明                   |
| ---- | ----------------------------------------------- | ------------ | ---------------------- |
| 输入 | 上层业务发送请求（连接 ID、报文类型、业务数据） | 各业务模块   | 业务层调用发送接口     |
| 输入 | 底层网络数据包                                  | Socket 接口  | 网络接收到的原始字节流 |
| 输入 | 连接建立 / 断开事件                             | 操作系统     | 连接状态变更通知       |
| 输出 | 上层业务接收回调（连接 ID、报文类型、业务数据） | →各业务模块  | 解析后分发给业务层     |
| 输出 | 网络字节流                                      | →Socket 接口 | 封装后发送到网络       |
| 输出 | 连接状态通知                                    | →业务层      | 通知连接建立 / 断开    |

#### 2.5.3 内部执行逻辑

1. 服务端连接管理与 IO 多路复用
   1. 服务端启动时创建监听 Socket，绑定端口，注册到 epoll 事件循环
   2. 监听线程阻塞等待 epoll 事件，收到新连接事件后 accept，创建连接会话对象
   3. 将新连接的 Socket 注册到 epoll，监听读事件
   4. 工作线程池处理读事件：从 Socket 读取数据到接收缓冲区
   5. 从缓冲区解析完整报文，校验魔数、版本、长度，丢弃非法报文
   6. 根据报文类型分发到对应业务模块的处理函数
   7. 业务模块处理完成后，将响应数据交给通信层，封装报文后写入发送缓冲区
   8. 监听写事件，将发送缓冲区数据批量发送到网络
2. 客户端连接管理
   1. 客户端启动后创建 Socket，发起 TCP 连接请求
   2. 连接成功后启动读线程，循环接收服务端数据
   3. 启动心跳线程，定时发送心跳报文
   4. 上层业务调用发送接口时，将数据封装报文后写入发送队列
   5. 发送线程从队列取数据，串行发送到网络
3. 粘包拆包处理
   - 采用固定报文头 + 变长消息体格式，报文头包含消息体长度字段
   - 接收时先读取固定长度报文头，解析出消息体长度
   - 再读取对应长度的消息体，组成完整报文
   - 剩余数据留在接收缓冲区，等待下一次读取
4. 断连重连机制
   1. 客户端检测到连接断开（读返回 0、写失败、心跳超时）
   2. 通知业务层连接断开，UI 提示重连中
   3. 采用指数退避算法重试：首次间隔 1s，二次 2s，三次 4s，最大间隔 30s
   4. 重连成功后，重新发起登录请求，同步最新状态
   5. 重连成功后，本地缓存的未发送消息自动补发

#### 2.5.4 核心业务规则

1. 采用 TCP 可靠传输协议，保障报文传输不丢失、不损坏
2. 报文格式统一，魔数 0x494D 校验合法性，版本号兼容后续迭代
3. 消息 ID 全局唯一，用于服务端去重与客户端幂等处理
4. 单连接串行发送报文，保障消息有序性
5. 心跳间隔 15 秒，超时 30 秒判定连接断开
6. 通信层与业务层完全解耦，底层替换为第三方网络库不影响业务逻辑

#### 2.5.5 依赖的外部资源

- 外部模块：所有上层业务模块
- 底层资源：Socket 系统调用、IO 多路复用接口（epoll/select）
- 内存资源：连接会话池、收发缓冲区、发送队列

#### 2.5.6 异常场景处理

1. **报文校验失败**：丢弃非法报文，记录日志，不断开连接
2. **缓冲区溢出**：单连接接收缓冲区超过 1MB 时，断开连接，避免内存溢出
3. **网络闪断**：自动触发重连，业务层无感知（除连接状态通知）
4. **消息重复发送**：服务端通过消息 ID 去重，重复报文直接丢弃，返回成功响应
5. **发送队列积压**：队列长度超过 100 时，丢弃最早的非重要报文（如状态通知），优先保障业务消息

### 2.6 数据持久化模块

#### 2.6.1 模块功能详述

本模块负责系统所有永久数据的存储与读取，为业务层提供统一的数据访问接口，屏蔽数据库操作细节。核心能力包括：数据增删改查、数据库连接池管理、事务控制、查询优化、数据一致性保障。 本模块采用轻量关系型数据库实现，适配 C++ 开发环境，满足中小规模数据存储需求。

#### 2.6.2 模块输入输出

表格

| 方向 | 输入项                                   | 数据来源    | 说明                       |
| ---- | ---------------------------------------- | ----------- | -------------------------- |
| 输入 | 数据查询请求（表名、查询条件、分页参数） | 各业务模块  | 业务层数据查询             |
| 输入 | 数据新增请求（表名、数据实体）           | 各业务模块  | 业务层写入数据             |
| 输入 | 数据更新请求（表名、更新字段、条件）     | 各业务模块  | 业务层修改数据             |
| 输入 | 数据删除请求（表名、删除条件）           | 各业务模块  | 业务层删除数据             |
| 输出 | 查询结果集                               | →各业务模块 | 返回查询到的数据           |
| 输出 | 操作结果（影响行数、错误码）             | →各业务模块 | 返回写入 / 更新 / 删除结果 |

#### 2.6.3 内部执行逻辑

1. 连接池管理
   1. 模块初始化时创建固定数量的数据库连接（默认 20 个），存入连接池
   2. 业务层发起数据操作请求时，从连接池获取空闲连接
   3. 操作完成后，连接归还连接池，不关闭
   4. 连接池定期检测连接有效性，失效连接自动重建
2. 数据操作流程
   1. 业务层调用对应数据访问接口，传入业务实体
   2. 数据访问层将业务实体转换为数据库字段，拼装 SQL 语句
   3. 从连接池获取数据库连接，执行 SQL
   4. 涉及多表操作时，开启事务，全部成功则提交，失败则回滚
   5. 将执行结果转换为业务实体返回给业务层
   6. 归还数据库连接到连接池
3. 查询优化逻辑
   - 所有查询条件优先使用索引字段
   - 历史消息查询强制分页，默认每页 20 条，避免全表扫描
   - 高频查询结果做短时内存缓存（5 秒），减少数据库压力
   - 批量插入采用预编译 SQL，提升写入性能

#### 2.6.4 核心业务规则

1. 核心业务数据变更实时写入数据库，保障持久化
2. 单业务多表操作必须使用事务，保障数据一致性
3. 用户删除消息为软删除，仅更新状态字段；会话删除为硬删除，物理清除数据
4. 数据库连接池大小根据并发量配置，禁止频繁创建销毁连接
5. 所有数据库操作均有错误处理，异常时返回明确错误码，不崩溃

#### 2.6.5 依赖的外部资源

- 外部模块：所有业务模块
- 数据库资源：SQLite/MySQL 轻量关系型数据库（毕设推荐 SQLite，部署简便）
- 系统资源：数据库连接池

#### 2.6.6 异常场景处理

1. **数据库连接失败**：重试 3 次仍失败则返回数据库不可用错误，业务层降级处理
2. **SQL 执行异常**：事务回滚，记录错误日志，返回操作失败
3. **连接池耗尽**：请求等待超时（3 秒）后返回连接池繁忙错误
4. **主键冲突**：返回数据已存在错误，业务层做对应处理
5. **查询超时**：单条查询超过 1 秒自动中断，避免阻塞业务线程

### 2.7 客户端 UI 交互模块

本模块是用户与系统交互的入口，负责所有界面渲染与用户操作捕获。核心能力包括：登录界面、主界面、私聊界面、群聊界面、个人信息界面、系统通知弹窗、状态展示、消息提示。 本模块仅负责展示与交互，不处理核心业务逻辑，所有业务判定均提交给客户端业务层。

1. **界面渲染异常**：捕获异常，显示错误提示，不导致程序崩溃
2. **数据更新失败**：保留旧数据，提示 “刷新失败，请重试”
3. **网络断开**：界面顶部显示 “连接已断开” 提示条，重连后自动消失

#### 3.2.3 接口调用规则

1. **请求 - 响应模式**：客户端主动发起的请求均对应响应报文，通过 seq 序列号匹配
2. **推送模式**：服务端主动向客户端推送消息、通知，无需客户端响应
3. **异步调用**：所有网络接口均为异步调用，客户端注册回调函数处理响应
4. **超时规则**：请求超时时间默认 3 秒，超时未收到响应则触发重试或失败
5. **有序性**：单连接内报文按发送顺序处理，响应与请求顺序一致

## 4 数据结构详细设计

### 4.1 核心业务实体结构

#### 4.1.1 用户信息结构体

```
enum UserStatus { OFFLINE = 0, ONLINE = 1 };
enum UserRole { ROLE_NORMAL = 0, ROLE_ADMIN = 1 };

struct UserInfo {
    int32_t userId;              // 用户ID，全局唯一
    std::string username;        // 预设账号名
    std::string nickname;        // 用户昵称
    UserStatus status;           // 在线状态
    UserRole role;               // 用户角色
    bool isBanned;               // 是否被封禁
    int64_t lastHeartbeat;       // 最后心跳时间戳（毫秒）
    int32_t connId;              // 绑定连接ID，离线为-1
    time_t createTime;           // 账号创建时间
    time_t updateTime;           // 最后更新时间
};
```

#### 4.1.2 消息结构体

```
enum MsgType { MSG_PRIVATE = 1, MSG_GROUP = 2 };
enum MsgStatus { MSG_NORMAL = 0, MSG_WITHDRAWN = 1, MSG_DELETED = 2 };

struct Message {
    uint64_t msgId;              // 全局唯一消息ID
    int32_t senderId;            // 发送者用户ID
    int32_t targetId;            // 目标ID：私聊为用户ID，群聊为群ID
    MsgType msgType;             // 消息类型
    std::string content;         // 消息文本内容
    int64_t sendTime;            // 发送时间戳（毫秒）
    MsgStatus status;            // 消息状态
};
```

#### 4.1.3 群组信息结构体

```
enum GroupStatus { GROUP_NORMAL = 0, GROUP_DISMISSED = 1 };

struct GroupInfo {
    int32_t groupId;             // 群组ID，全局唯一
    std::string groupName;       // 群组名称
    int32_t ownerId;             // 群主用户ID
    GroupStatus status;          // 群组状态
    time_t createTime;           // 创建时间
    time_t updateTime;           // 最后更新时间
    std::vector<int32_t> memberIds; // 群成员ID列表
};
```

#### 4.1.4 连接会话结构体（服务端）

```
struct Connection {
    int32_t connId;              // 连接ID
    int socketFd;                // Socket文件描述符
    int32_t userId;              // 绑定用户ID，未登录为-1
    bool isLogin;                // 是否已登录
    std::string recvBuffer;      // 接收缓冲区
    std::string sendBuffer;      // 发送缓冲区
    int64_t lastActiveTime;      // 最后活跃时间戳
};
```

### 4.2 缓存与队列数据结构

#### 4.2.1 在线用户缓存

- 数据结构：`std::unordered_map<int32_t, UserInfo> onlineUserMap`
- Key：用户 ID
- Value：用户完整信息
- 特性：O (1) 时间复杂度查找，用户上线插入，离线删除，仅存储在线用户
- 容量上限：150 条（预留 50% 并发冗余）

#### 4.2.2 连接会话映射表

- 数据结构：`std::unordered_map<int32_t, Connection*> connMap`
- Key：连接 ID
- Value：连接会话指针对象
- 特性：管理所有活跃连接，连接建立插入，断开释放资源

#### 4.2.3 离线消息队列

- 数据结构：`std::unordered_map<int32_t, std::queue<Message>> offlineMsgQueue`
- Key：接收用户 ID
- Value：该用户的离线消息队列，先进先出
- 特性：用户上线后批量取出投递，投递后清空
- 持久化：同时写入数据库，内存队列仅作加速用

#### 4.2.4 发送消息队列

- 数据结构：`std::queue<Packet> sendQueue`（单连接维度）
- 特性：异步发送缓冲，避免业务线程阻塞
- 容量上限：100 条，超过则丢弃低优先级报文

### 5.3 资源存储规则

本版本仅支持纯文本消息，不涉及图片、语音、文件等多媒体资源存储，所有消息内容均存储于数据库文本字段中。 后续版本扩展多媒体功能时，遵循以下规则：

1. 文件存储路径：`/data/im/files/[消息类型]/[年]/[月]/[日]/`
2. 文件命名规则：`[消息ID].[文件后缀]`
3. 数据库新增文件资源表，存储消息 ID 与文件路径的映射关系
4. 大文件采用分片存储，支持断点续传

## 6 核心流程详细时序设计

### 6.1 用户登录与离线消息补发时序

1. 客户端用户输入账号，点击登录，客户端封装`LOGIN_REQ`报文发送至服务端
2. 服务端通信层解析报文，分发至用户状态模块
3. 用户状态模块调用数据持久层查询`t_user`表，校验账号存在性
4. 调用权限管控层校验账号封禁状态
5. 校验通过：更新内存在线用户表，绑定连接 ID，更新用户最后心跳时间
6. 服务端向所有在线客户端广播`STATUS_NOTIFY`（该用户上线）
7. 服务端向当前客户端返回`LOGIN_RSP`（成功，携带用户信息）
8. 用户状态模块异步调用数据持久层，查询该用户的`t_offline_message`表
9. 按发送时间升序取出所有离线消息，关联消息表获取完整消息内容
10. 服务端向客户端批量推送`OFFLINE_MSG_PUSH`报文
11. 客户端接收后按顺序渲染到聊天界面
12. 服务端删除该用户已投递的离线消息记录

### 6.2 点对点聊天时序

1. 发送方用户在私聊界面输入消息，点击发送
2. 客户端业务层生成本地临时消息，UI 显示 “发送中” 状态
3. 客户端封装`PRIVATE_MSG_REQ`报文发送至服务端
4. 服务端通信层解析，分发至私聊业务模块
5. 校验发送者登录状态、接收者账号合法性、消息内容长度
6. 生成全局唯一 msgId，写入`t_message`表，状态为正常
7. 查询接收者在线状态：
   - 在线：直接向接收者推送`PRIVATE_MSG_PUSH`报文
   - 离线：写入`t_offline_message`表
8. 服务端向发送方返回`PRIVATE_MSG_RSP`（成功，携带 msgId 与服务端时间）
9. 发送方客户端更新消息状态为 “已发送”
10. 接收方客户端收到推送后，渲染消息，触发未读提示

### 6.3 群聊消息发送时序

1. 用户在群聊界面发送消息，客户端封装`GROUP_MSG_REQ`报文
2. 服务端群聊模块校验：用户是否在群内、群状态是否正常、消息合法性
3. 校验通过后生成全局 msgId，写入`t_message`表（消息类型为群聊）
4. 查询该群所有成员 ID 列表
5. 批量查询成员在线状态，分为在线列表与离线列表
6. 遍历在线成员，逐个推送`GROUP_MSG_PUSH`报文
7. 遍历离线成员，批量写入`t_offline_message`表
8. 向发送方返回`GROUP_MSG_RSP`成功响应
9. 在线群成员客户端收到推送，更新群聊界面

### 6.4 消息撤回时序

1. 用户在聊天界面长按消息，点击撤回，客户端发送`MSG_WITHDRAW_REQ`
2. 服务端私聊 / 群聊模块查询消息记录，校验：
   - 发送者是否为当前操作用户
   - 消息是否未撤回、未删除
   - 当前时间与发送时间差是否≤120 秒
3. 校验通过：更新`t_message`表`msg_status`为已撤回
4. 向会话所有参与方推送`MSG_WITHDRAW_NOTIFY`报文
5. 双方客户端收到通知后，将对应消息替换为 “消息已撤回” 提示
6. 校验失败：返回错误码（超时 / 无权限 / 消息不存在），客户端提示撤回失败

### 6.5 断连重连恢复时序

1. 客户端检测到连接断开（心跳超时 / 网络错误）
2. 客户端通信层通知业务层，UI 显示 “连接断开，正在重连”
3. 启动重连定时器，首次 1 秒后尝试重新建立 TCP 连接
4. 连接失败则指数退避（2s、4s、8s… 最大 30s），循环重试
5. 连接成功后，客户端重新发送`LOGIN_REQ`报文
6. 服务端执行登录逻辑，返回登录成功响应
7. 客户端拉取最新会话列表、用户在线状态
8. 客户端本地缓存的未发送消息按顺序补发
9. 服务端校验补发消息，通过 msgId 去重
10. 客户端 UI 恢复正常，提示 “连接已恢复”

### 6.6 系统启动时序

#### 服务端启动

1. 加载配置文件（端口号、数据库路径、连接池大小等）
2. 初始化数据持久层：创建数据库连接池，检查表结构，不存在则自动创建
3. 初始化权限管控模块：加载管理员角色配置
4. 初始化业务模块：用户状态、私聊、群聊模块初始化
5. 初始化通信层：创建监听 Socket，绑定端口，启动 epoll 事件循环
6. 启动心跳检测线程、离线消息处理线程
7. 服务进入就绪状态，日志输出 “服务启动成功，监听端口 XXX”

#### 客户端启动

1. 初始化 UI 框架，渲染登录界面
2. 初始化客户端通信层，创建 Socket
3. 初始化客户端业务层，加载本地缓存
4. 等待用户输入账号，触发登录流程

## 7 性能与资源控制设计

### 7.1 并发连接处理

1. **IO 多路复用模型**：服务端采用 epoll 水平触发模式，单监听线程 + 多工作线程架构，支撑 100 并发连接无压力
2. **连接上限控制**：最大连接数设置为 150（预留 50% 冗余），超过阈值时拒绝新连接，返回 “系统繁忙”
3. **连接资源隔离**：每个连接分配独立的收发缓冲区，默认各 10KB，单连接缓冲区溢出则断开连接，避免影响其他用户
4. **线程池调度**：业务逻辑交给固定大小线程池（默认 8 线程）处理，避免线程频繁创建销毁，提升并发处理效率

### 7.2 消息推送限流

1. **单用户发送限流**：普通用户每秒最多发送 5 条消息，超过则返回 “发送过于频繁” 错误，防止恶意刷屏
2. **群消息批量推送优化**：群消息推送采用异步队列，单群每秒推送不超过 20 条，避免瞬时网络风暴
3. **全量广播限流**：用户上下线、昵称修改等全量广播采用分批发送，每批 10 个连接，间隔 10ms
4. **低优先级报文丢弃**：网络拥塞时，优先保障聊天消息，可丢弃状态同步、通知类低优先级报文

### 7.3 数据库查询优化

1. **索引优化**：所有查询条件字段均建立合适索引，核心查询走索引，避免全表扫描
2. **分页查询**：历史消息、群成员列表等批量查询强制分页，默认单页 20 条，禁止一次性加载全量数据
3. **连接池复用**：数据库连接池大小设置为 20，复用连接减少连接开销，连接池耗尽时请求排队等待
4. **读写分离思想**：高频读操作优先查询内存缓存，写操作实时落库，降低数据库压力
5. **批量操作优化**：批量插入、批量查询采用预编译 SQL 与批量执行接口，减少交互次数

### 7.4 缓存资源占用控制

1. **在线用户缓存**：仅存储在线用户信息，用户离线立即移除，内存占用与在线用户数线性相关
2. **离线消息存储**：离线消息直接持久化到数据库，服务端内存不做长期缓存，仅投递时临时加载
3. **发送队列限制**：单连接发送队列最大长度 100，超过则丢弃旧的非关键报文
4. **内存监控**：服务端定期检测内存占用，超过阈值时触发缓存清理，优先清理过期临时数据

### 7.5 时延保障措施

1. **业务逻辑轻量化**：核心消息转发路径尽量减少计算，数据库操作异步化
2. **零拷贝优化**：报文收发尽量减少内存拷贝，提升传输效率
3. **心跳报文优先**：心跳报文优先级高于业务报文，保障连接状态实时性
4. **关键路径无锁**：核心转发路径采用无锁数据结构，减少线程竞争开销
5. **数据库慢查询监控**：超过 100ms 的查询记录日志，持续优化
