# IM即时通讯系统概要设计说明书

# 1 引言

## 1\.1 编写目的

本文档为《IM即时通讯系统》的软件概要设计说明书，基于项目软件需求规格说明书（SRS）进行宏观架构设计与模块拆解，明确系统整体架构、模块划分、技术选型、数据设计、性能指标及风险预案。本文档面向软件开发、测试、评审人员，是系统详细设计、代码开发、功能测试、项目验收的核心依据。

本设计严格遵循高内聚、低耦合的软件工程设计原则，采用C\+\+技术栈完成宏观架构规划，不涉及底层具体代码实现，仅聚焦系统整体框架、模块职责、接口规范与部署拓扑，适配毕业设计及工程训练项目验收标准。

## 1\.2 项目背景

本项目为后端训练级即时通讯（IM）系统，采用客户端与服务端分离的工业级部署架构，核心落地点对点私聊、群聊全业务流程，配套用户权限管控、消息管理、系统管理员运维能力。系统本版本聚焦核心通讯业务实现，暂不落地高级安全加固、高可用容错、多媒体消息等扩展能力，预留后续迭代优化空间，主要用于工程开发训练、项目落地与标准化指标验收。

系统区分普通用户、群主（群管理员）、系统管理员三类角色，构建分层权限管控体系，实现基础即时通讯全场景业务闭环，满足100人并发在线、低时延消息投递的核心性能要求。

## 1\.3 术语与缩略语

|术语/缩略语|释义|
|---|---|
|IM|即时通讯（Instant Messaging），实时网络消息交互系统|
|SRS|软件需求规格说明书，定义系统功能、非功能需求与验收标准|
|点对点私聊|两个独立用户之间的一对一文本消息交互场景，支持离线消息投递|
|群聊|多用户组成群组，实现多人实时文本消息交互的业务场景|
|系统管理员|全局超级权限角色，负责用户封禁、群聊强制解散、全量聊天记录查看|
|群主|普通用户建群后自动生成的群内管理员，仅拥有单群局部管理权限|
|离线消息|用户离线期间接收的消息，用户上线后自动投递展示|

## 1\.4 设计约束

本系统概要设计严格遵循以下约束条件，所有设计方案均不突破边界：

1. **技术栈约束**：全程基于C\+\+语言进行架构设计，不引入其他核心开发语言；

2. **设计层级约束**：仅做宏观概要设计，不涉及底层代码编写、具体算法实现；

3. **架构约束**：严格采用客户端\-服务端分离架构，保证分层清晰、模块解耦；

4. **需求边界约束**：仅实现SRS定义的本版本核心功能，不拓展多媒体消息、用户注册、安全加密等未约定功能；

5. **质量约束**：满足100用户并发、消息投递时延≤400ms的量化性能指标。

# 2 总体架构设计

## 2\.1 架构选型

结合IM系统实时交互、高并发连接、消息持久化的核心特性，以及C\+\+技术栈的高性能、高并发优势，本系统采用**客户端\-服务端（C/S）分层架构**，同步采用事件驱动、网络IO多路复用的设计思想，适配即时通讯系统实时消息投递的业务场景。

相较于B/S架构，C/S架构客户端轻量化、响应速度快、实时性强，更适配桌面端IM即时交互需求，同时服务端独立部署，可实现业务逻辑、数据存储、网络通信的完全解耦，符合工业级工程部署规范。

## 2\.2 系统分层架构

系统整体分为**客户端三层架构**与**服务端四层架构**，全程遵循高内聚、低耦合原则，各层级职责单一、层级调用单向闭环，无跨层乱调用情况。

### 2\.2\.1 客户端分层（表现层、业务层、通信层）

1. **表现层（UI交互层）**：负责所有前端界面展示与用户交互，包含登录界面、私聊界面、群聊界面、个人信息设置界面、系统通知弹窗。实现用户昵称展示、在线状态渲染、消息列表刷新、撤回提示、封禁提示、发送失败红感叹号等所有可视化能力。

2. **客户端业务层**：承接表现层交互请求，处理客户端本地业务逻辑，包含用户登录校验、本地会话管理、消息本地缓存、消息撤回/删除本地逻辑、新消息通知、昵称实时同步刷新等功能，对接服务端完成数据交互。

3. **客户端通信层**：基于C\+\+网络编程实现，负责与服务端建立长连接、网络数据收发、报文封装与解析、异常重连，保障消息实时传输，屏蔽底层网络细节。

### 2\.2\.2 服务端分层（通信层、业务层、权限管控层、数据持久层）

1. **服务端通信层**：核心承载网络并发能力，基于IO多路复用监听客户端长连接，处理连接建立、断开、心跳检测、消息报文解析与转发，支撑100用户并发在线，保障消息投递低时延。

2. **服务端业务层**：系统核心业务处理层，包含私聊业务、群聊业务、用户状态管理三大核心业务模块，处理消息收发、离线消息存储、历史消息查询、会话管理、消息撤回/删除等核心逻辑。

3. **权限管控层**：独立的权限校验与运维管控层级，区分普通用户、群主、系统管理员三类角色，实现用户封禁、强制踢线、群聊解散、全量数据查询等管控能力，严格隔离不同角色权限边界。

4. **数据持久层**：负责系统所有业务数据的持久化存储与读取，对接数据库完成用户数据、群组数据、聊天记录、会话数据的增删改查，保障持久化数据不丢失。

## 2\.3 部署拓扑设计

本系统采用**客户端、服务端完全分离的独立部署拓扑**，为标准工业级部署架构，拓扑结构如下：

1. **服务端节点**：独立部署于服务器设备，单独启动服务进程，持续监听指定网络端口，统一处理所有客户端的连接请求、消息交互、数据存储、权限管控等核心业务，为所有客户端提供统一服务支撑。服务端支持独立启停、独立运维，不依赖客户端运行。

2. **客户端节点**：多终端独立部署，每个用户终端单独运行客户端程序，通过网络与服务端建立长连接，所有用户交互数据、消息数据均通过服务端中转处理，客户端仅负责交互展示与本地轻量逻辑处理。

3. **数据存储节点**：与服务端绑定部署，数据库独立运行，为服务端提供持久化数据支撑，存储系统全量业务数据。

部署特性：单服务端、多客户端的分布式交互模式，架构简洁清晰，满足工程化部署规范，适配本版本训练级项目需求。服务端重启后内存会话数据丢失为版本容忍缺陷，不影响整体部署架构合规性。

# 3 系统模块划分与接口设计

基于分层架构与业务边界，将系统拆解为7个核心独立模块，各模块高内聚、职责单一，模块间通过标准化接口通信，无功能冗余、无逻辑交叉。

## 3\.1 核心模块划分及职责

### 3\.1\.1 用户登录与状态管理模块

**所属层级**：客户端业务层\+服务端业务层\+权限管控层

**核心职责**：

1. 实现预设账号登录校验，无自主注册能力，校验账号合法性与封禁状态；

2. 管理用户在线/离线二态状态，实时同步全网用户状态至各客户端；

3. 处理封禁用户登录拦截，展示封禁提示，对在线封禁用户执行强制踢下线操作；

4. 支持用户昵称修改，实现全网会话端实时同步刷新最新昵称；

5. 维护用户长连接心跳，检测用户上下线状态变更。

### 3\.1\.2 点对点私聊模块

**所属层级**：客户端业务层\+服务端业务层\+数据持久层

**核心职责**：

1. 实现一对一文本消息实时收发、离线消息缓存与上线自动投递；

2. 消息发送异常处理，客户端展示红色感叹号失败标识；

3. 会话初始化自动加载最近20条历史私聊消息；

4. 支持用户无痕删除本人单条消息、2分钟内消息撤回及超时拦截；

5. 支持用户删除整条私聊会话，服务端彻底清空对应会话数据；

6. 私聊新消息本地通知提示功能。

### 3\.1\.3 群聊管理模块

**所属层级**：客户端业务层\+服务端业务层\+数据持久层

**核心职责**：

1. 支撑普通用户建群，自动赋予创建者群主权限；

2. 实现群成员管理：群主可移除成员、全员可邀请成员、主动退群；

3. 支持全员修改群名称，修改后全网实时同步生效；

4. 群会话默认加载最近20条群历史消息，支持群消息撤回、本人消息删除；

5. 接收服务端群解散指令，触发全员解散通知；

6. 群聊新消息通知提示，保障多用户群交互实时性。

### 3\.1\.4 系统管理员管控模块

**所属层级**：服务端权限管控层\+数据持久层

**核心职责**：

1. 全局权限管控，独立于群组权限体系，不受局部群权限限制；

2. 全量数据查询：可查看任意用户、任意群组的完整聊天记录，不受客户端消息删除、会话删除影响；

3. 用户封禁管理：封禁普通账号、拦截封禁账号登录、强制踢下线在线封禁用户；

4. 群聊管控：强制解散平台任意群聊，自动推送解散通知至所有群成员。

### 3\.1\.5 网络通信模块

**所属层级**：客户端通信层\+服务端通信层（独立隔离通信层，与业务层完全解耦）

**核心职责**：

1. **通信隔离适配**：采用**通信层抽象封装设计**，搭建统一网络通信适配接口，隔离底层网络实现细节，支持原生Socket、第三方网络库无缝切换，上层业务模块无感知，不影响私聊、群聊、权限管控等核心业务逻辑；

2. 统一消息报文封装、解析、校验，定义标准化通信协议，屏蔽不同网络库的接口差异，保证数据传输格式统一、完整；

3. 服务端实现IO多路复用并发模型，依托抽象通信接口实现100用户并发连接支撑，底层通信实现可灵活替换；

4. 处理网络异常、连接心跳检测、断连重连、报文重传逻辑，封装通用通信容错能力，与业务逻辑解耦；

5. 统一消息转发调度，实现私聊、群聊消息的精准投递，对外提供标准化消息推送、接收、回调接口。

### 3\.1\.6 数据持久化模块

**所属层级**：服务端数据持久层

**核心职责**：

1. 负责用户信息、群组信息、成员关系、聊天记录、会话数据的持久化存储；

2. 响应业务模块的数据查询、新增、修改、删除请求；

3. 持久化离线消息，保障用户上线后正常接收；

4. 永久留存全量聊天数据，支撑管理员全局查询能力；

5. 响应会话删除指令，彻底清空对应会话持久化数据。

### 3\.1\.7 客户端UI交互模块

**所属层级**：客户端表现层

**核心职责**：

1. 提供所有系统操作界面，接收用户点击、输入、编辑等交互行为；

2. 实时渲染用户在线状态、昵称、消息列表、历史消息；

3. 展示各类业务提示：封禁提示、撤回提示、发送失败红感叹号、群解散通知；

4. 实现新消息通知、界面数据实时刷新能力。

## 3\.2 模块间接口定义（宏观接口）

所有模块间采用**标准化函数接口/网络报文接口**通信，接口单向调用，规避循环依赖，核心接口定义如下：

1. **UI模块→客户端业务模块接口**：登录请求、昵称修改请求、消息发送请求、消息撤回/删除请求、会话删除请求、群操作请求，仅传递用户操作指令，不处理业务逻辑。

2. **客户端业务模块→通信模块接口**：业务数据封装、网络发送请求、数据接收回调，将本地业务请求转为网络报文传输。

3. **服务端通信模块→服务端业务模块接口**：网络报文解析、业务请求分发、消息转发回调，将客户端请求分发至对应业务模块。

4. **服务端业务模块→数据持久层接口**：数据增删改查请求、离线消息存储请求、历史数据查询请求、会话数据清空请求。

5. **权限管控层→业务模块接口**：权限校验接口、用户封禁指令、群解散指令、全量数据查询接口，管控所有高危操作权限。

6. **服务端→客户端通信回调接口**：消息推送、状态同步、通知推送、操作结果回调，实现客户端数据实时更新。

# 4 数据总体设计

## 4\.1 数据存储方案选型

结合本系统业务特性、性能需求及版本约束，采用**「数据库持久化存储\+服务端内存临时缓存」**的双层存储方案，无本地文件自定义存储，方案适配C\+\+服务端架构，兼顾性能与数据可靠性。

1. **持久化存储（核心）**：选用轻量关系型数据库，存储系统所有永久业务数据，包括用户基础信息、群组信息、群成员关系、全量聊天记录、会话信息、用户封禁状态数据。数据永久落地，断电、重启不丢失，支撑历史消息查询、管理员全量数据查看、会话删除数据清空等核心能力。

2. **内存临时缓存（辅助）**：服务端内存缓存实时在线用户状态、当前活跃会话、待投递离线消息等临时数据，用于提升消息投递、状态查询的响应速度，满足≤400ms时延要求。**版本容忍缺陷**：服务端重启后内存临时数据丢失，本版本不做优化，预留后续迭代。

## 4\.2 核心数据实体设计（宏观）

基于业务场景，梳理系统5大核心数据实体，定义核心字段，无冗余设计：

1. **用户信息表**：存储预设账号、用户名、昵称、登录状态、封禁状态、角色类型（普通用户/管理员）、创建时间；

2. **群组信息表**：存储群ID、群名称、群主ID、创建时间、群状态（正常/解散）；

3. **群成员表**：存储群ID、用户ID、入群时间，关联用户与群组关系；

4. **消息记录表**：存储消息ID、发送者ID、接收者ID/群ID、消息内容、发送时间、消息类型（私聊/群聊）、撤回状态、删除状态；

5. **会话信息表**：存储会话ID、会话类型（私聊/群聊）、关联用户/群组ID、创建时间、最后消息时间、会话状态。

## 4\.3 数据读写规则

1. 用户、群组、消息核心数据变更实时写入数据库，保障数据持久化；

2. 用户在线状态、活跃会话等临时数据仅内存存储，定时同步校验；

3. 用户删除本人消息仅修改单条消息状态，不删除原始数据（保障管理员可查询全量记录）；

4. 用户删除私聊会话，服务端彻底删除对应会话所有消息数据，不可恢复；

5. 群解散后，标记群组状态为解散，留存历史数据供管理员查询。

# 5 关键技术选型

本系统基于**C\+\+11及以上版本**开发，所有技术选型贴合高性能、轻量级、适配IM实时通讯场景，严格匹配项目约束，无过度技术堆叠。

## 5\.1 核心开发技术

1. **核心编程语言**：C\+\+，依托其高性能、低内存开销、高并发处理能力，支撑100用户并发与低时延消息投递，适配服务端后台开发。

2. **网络通信技术**：采用**抽象通信适配层\+可替换底层实现**架构，默认基于C\+\+ Socket实现TCP长连接与IO多路复用，预留第三方网络库适配接口（如Asio、libevent等），通过统一封装屏蔽底层差异，支持后期无缝替换通信底层，业务层无需改造；

3. **多线程技术**：服务端采用多线程模型，分离连接监听、消息接收、消息处理、数据存储任务，避免单线程阻塞，保障并发处理能力。

## 5\.2 数据存储技术

采用轻量关系型数据库，支持标准SQL语句，适配C\+\+数据读写，满足本系统中小体量数据存储需求，部署简单、运维便捷，适配毕业设计与工程训练项目场景。

## 5\.3 客户端交互技术

客户端基于轻量化桌面UI框架开发，实现界面渲染、事件监听、数据刷新，适配C\+\+客户端开发生态，满足基础交互与可视化展示需求。

## 5\.4 技术选型约束说明

1. 本版本不引入Redis、消息队列等中间件，简化架构，贴合训练级项目定位；

2. 不实现密码加密、接口校验、数据加密等安全技术，预留后续迭代；

3. 仅支持文本消息解析与传输，不适配多媒体文件处理技术；

4. 网络层采用解耦隔离设计，预留第三方网络库拓展能力，支持后期通信底层技术迭代升级。

# 6 系统非功能指标设计

## 6\.1 性能指标（可量化、可验收）

严格对标SRS定义的量化标准，本系统最终需满足以下性能指标：

1. **并发性能**：服务端支持**最大100名用户同时在线并发**，满并发状态下系统无卡顿、无连接丢失、消息无堆积。

2. **响应时延**：正常网络环境下，点对点、群聊消息投递响应时间 **≤400ms**，用户操作反馈实时无明显延迟。

3. **加载性能**：打开私聊/群聊会话，20条历史消息瞬时加载完成，无卡顿等待。

4. **同步性能**：用户昵称修改、群名称修改、用户上下线状态变更，全网客户端同步刷新时延≤500ms。

## 6\.2 可靠性指标

1. **消息可靠性**：在线消息100%投递成功，离线消息可稳定缓存，用户上线后自动完整投递，无消息丢失、乱序问题。

2. **权限可靠性**：角色权限严格隔离，群主仅拥有单群管理权限，系统管理员全局权限生效精准，无越权、权限失效问题。

3. **数据可靠性**：持久化数据稳定不丢失，会话删除、消息删除、群解散等数据操作精准执行，符合业务规则。

4. **容错性**：网络异常时消息标记发送失败并展示红感叹号，不崩溃、不报错退出；单用户连接异常不影响其他用户正常使用。

## 6\.3 可维护性与可扩展性

1. **可维护性**：模块划分清晰、职责单一，接口规范统一，代码层级分明，便于后期测试、Bug修复与运维迭代；

2. **可扩展性**：架构预留扩展接口，后续可快速迭代多媒体消息、安全加密、高可用容错、数据备份、在线状态细化等功能，无需重构整体架构。

# 7 风险分析与应对方案

结合系统架构、技术栈、版本约束与运行环境，识别本版本核心风险点，对应制定可落地的应对方案。

## 7\.1 性能风险

**风险描述**：满100用户并发场景下，出现消息堆积、投递时延超标、连接断开等问题，无法满足性能验收指标。

**应对方案**：优化服务端IO多路复用与多线程调度逻辑，合理分配线程任务，避免线程阻塞；精简消息报文格式，减少网络传输开销；限制单用户消息发送频率，防止恶意刷屏导致系统过载，保障并发稳定性。

## 7\.2 数据丢失风险

**风险描述**：服务端重启后，内存中缓存的临时会话数据、未投递离线消息丢失，影响用户体验（本版本为容忍缺陷）。

**应对方案**：本版本明确接纳该缺陷，在文档与验收标准中明确边界；后续迭代版本可优化为内存数据定时持久化，规避重启数据丢失问题。

## 7\.3 网络异常风险

**风险描述**：用户网络波动、断网重连时，出现消息重复发送、状态同步异常、会话错乱等问题。

**应对方案**：增加消息唯一ID标识，服务端做消息去重处理；优化心跳检测机制，精准判定用户在线/离线状态；依托隔离通信层封装通用重连、容错逻辑，无论底层采用原生Socket或第三方网络库，均可统一适配网络异常、断网重连场景，重连后同步最新用户状态与会话数据。

## 7\.4 权限越权风险

**风险描述**：角色权限校验失效，出现普通用户拥有管理员权限、群主跨群管理、封禁用户可正常登录等越权问题。

**应对方案**：服务端所有管控操作前置权限校验逻辑，严格区分三类角色权限边界；单独封装权限校验模块，统一拦截所有高危操作，避免权限漏洞。

## 7\.5 功能逻辑异常风险

**风险描述**：消息撤回超时拦截、会话彻底删除、群解散通知等核心逻辑失效，不符合需求规范。

**应对方案**：服务端统一管控业务规则，所有时间校验、数据删除、通知推送逻辑由服务端判定，不依赖客户端本地逻辑，规避客户端篡改、逻辑失效问题。
